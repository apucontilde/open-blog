A multi-tenant blog platform: one authoring API, many public sites

One REST API backs an editor UI for writing and publishing markdown posts, and any number of independent reader sites. Tenants are data-isolated by the database itself (PostgreSQL row-level security), authentication covers email+password plus Google/GitHub SSO, and images live in Cloudflare R2 (decision adopted). This plan is deliberately framework- and language-agnostic.

RBAC + RLS tenancy

Horizontally scalable

Adopted defaults for this review

Each default is applied in the plan below. Flag any you want changed during review; that's the purpose of this document.

  • REST over GraphQL — public API scales < cache/CDN
  • Opaque session tokens in DB (revocable), not stateless JWT
  • Shared PostgreSQL schema + row-level security per tenant
  • Shared R2 bucket with per-tenant key prefix
  • Email+password kept as optional fallback alongside SSO
  • Auth lives in the same backend as posts — no third-party IdP service
  • GFM + server-side syntax highlighting for rendering
  • Invite by email + role-baked invite links
  • Image variants (480/800/1200 + WebP) generated at upload

Goal & scope

Authoring side

One editor UI (per tenant or cross-tenant for admins) writes markdown posts in an interactive live-preview editor, manages draft → publish lifecycle, uploads images — and imports existing documents (PDF · DOCX · Google Docs · open formats) straight into markdown drafts. All mutations go through the authenticated admin API.

Reading side

Many independent reader UIs, each mapped to exactly one tenant (by slug/subdomain). They consume a cachable read-only public API and render sanitized HTML. Public UIs never hold credentials.

Out of scope

Comments, search index, subscriptions/newsletters, translation, A/B tools. Deltas are noted in risks so they don't sneak into the schema later.

User stories — API behavior by persona

Each story pins down exact API behavior with Given / When / Then acceptance criteria. These are the contract tests the implementation must pass; IDs (ST-1 … ST-23) are referenced from build tasks. Roles come from the authorization matrix in section 5.

Guests & reader sites — "any visitor reads a site"
ST-1 Guest reads a published post from a reader site
  • Given tenant alpha has post hello-world with status published
  • When GET /public/alpha/posts/hello-world
  • Then 200 with title, excerpt, sanitized HTML body, author display name, published_at, and image URLs
  • And response carries ETag + Cache-Control so edge caching serves repeat reads
ST-2 Guest never sees a draft
  • Given tenant alpha has post draft-idea with status draft
  • When guest calls GET /public/alpha/posts/draft-idea
  • Then the API returns 404, indistinguishable from a slug that does not exist — drafts are not enumerable via the public API
ST-3 Each site is isolated to its own tenant
  • When a reader site bound to beta lists posts via GET /public/beta/posts
  • Then results contain only beta's published posts; identical slugs in alpha are independent namespaces
  • And listing excludes archived posts
ST-4 Guest paginates a site listing
  • Given a site has more published posts than one page
  • When GET /public/alpha/posts?before=<cursor>
  • Then a keyset cursor (next_cursor) is returned, newest-first; list payloads carry metadata only (no markdown body)
Author — "I write my own posts"
ST-5 Author creates a draft
  • Given the author has a session with active tenant alpha (role author)
  • When POST /admin/posts with {title, content_markdown}
  • Then 201, status = draft, author_id = me, tenant from the session (any client-supplied tenant field is ignored)
  • And the draft is not visible through /public (ST-2 behavior)
ST-6 Author edits own draft, not others'
  • Given the author's own draft :id
  • When PATCH /admin/posts/:id
  • Then 200, markdown/metadata updated, updated_at bumped
  • When the same author targets another author's draft in the same tenant
  • Then 403, and that draft is absent from GET /admin/posts
ST-7 Author uploads an image into a draft
  • When POST /admin/media/presign with {post_id}
  • Then 201 with a short-lived presigned PUT URL whose key is pinned to the tenant's prefix (cannot name another tenant's object)
  • When the author PUTs bytes to R2, then calls POST /admin/media/confirm
  • Then a post_images row is recorded, a worker generates the 480/800/1200 + WebP variants, and the markdown may reference the CDN URL
ST-8 Author cannot publish, nor edit published posts
  • When POST /admin/posts/:id/publish or PATCH /admin/posts/:id on a published post
  • Then 403 — publishing and published-post edits require editor+
ST-23 Author imports a document into a draft as markdown
  • When POST /admin/imports with a file (PDF · DOCX · ODT · RTF · HTML) or {source: "google_docs"}
  • Then 202 {import_id, status: "converting"}; the original is stored and handed to the conversion worker
  • And GET /admin/imports/:id returns status, the converted markdown preview, and a per-format fidelity warning when the conversion may be lossy (e.g. PDF)
  • When POST /admin/imports/:id/apply
  • Then a draft is created under the exact ST-5 rules (status draft, author_id = me, tenant from session) with content_markdown set to the converted body, and the import row records post_id
  • When the conversion fails or the format is unsupported
  • Then GET /admin/imports/:id reports an error plus a remediation hint and no post is ever partially created
  • When source: "google_docs"
  • Then the worker exports the document through the author's linked Google identity (identities); a linked account lacking the drive.readonly export scope is sent through a re-consent flow first
Editor — "I curate and publish"
ST-9 Editor publishes any draft in the tenant
  • Given a draft exists in the editor's tenant (own or another author's)
  • When POST /admin/posts/:id/publish
  • Then 200, status = published, published_at set server-side
  • And immediately visible: caches for this tenant are purged and ST-1 now returns 200
ST-10 Editor unpublishes / archives
  • When POST /admin/posts/:id/unpublish
  • Then status = draft; guest reads return 404 and caches are purged for that tenant
  • And status = archived hides it from public listing while keeping admin edit access for editor+
ST-11 Editor edits any post in the tenant
  • Given any post (any author, draft or published) in the editor's tenant
  • When PATCH /admin/posts/:id
  • Then 200; a published post's public representation reflects the edit with cache invalidation, and published_at is unchanged
Tenant admin & owner — "I manage people and the site"
ST-12 Admin invites a member by email (SSO join)
  • When POST /admin/members with {email, role: "editor"} — or the admin generates a role-baked tenant invite link
  • Then 201 and an invitation row is stored for that tenant
  • And the invitee joins on first sign-in: an email invite consumes only when the SSO email is verified and matches; a link invite skips straight to the link's baked role. Repeat sign-ins are idempotent
ST-13 Admin changes a member's role — effective immediately
  • When PATCH /admin/members/:userId with a new role
  • Then 200; the change applies on the member's next request — sessions re-resolve membership per request, no re-login
  • And demoting to a weaker role (e.g. author) immediately revokes the removed capabilities (403)
ST-14 Admin removes a member
  • When DELETE /admin/members/:userId
  • Then 204; the removed user's active session immediately loses tenant access (403)
ST-15 Owner manages tenant settings
  • When owner calls PATCH /admin/tenants/:id (site name, branding, SEO defaults)
  • Then 200; reader sites see the change on GET /public/:slug/site after cache invalidation
  • And owner may DELETE /admin/tenants/:id → 204; a tenant admin may not (403)
Super admin — "I run the whole platform"
ST-16 Super admin provisions a new tenant site
  • When POST /admin/tenants with a new unique slug
  • Then 201; tenant row, R2 key prefix, and RLS run-as role are created atomically
  • When the slug is already taken
  • Then 409; no partial tenant is created
ST-17 Super admin reads across every tenant without membership
  • When GET /admin/tenants, then GET /admin/posts?tenant=beta
  • Then all tenants and cross-tenant rows are returned (RLS bypass), including drafts, with no memberships row required
ST-18 Super admin switches active scope and acts
  • When PUT /auth/me/active-tenant with a tenant id from the platform list
  • Then subsequent admin calls operate in that tenant scope (create, edit, publish any post) — same session, no re-login
Cross-cutting — auth, sessions, performance
ST-19 First SSO sign-in links account + memberships
  • Given a verified Google/GitHub identity and a pending invitation for the same email
  • When the OAuth callback completes
  • Then the user + identities row are upserted, the invitation is consumed, a session is issued, and repeating the flow never duplicates rows
ST-20 User with several memberships switches active tenant
  • When PUT /auth/me/active-tenant with one of their member tenants
  • Then 200; every later admin call in that session is RLS-scoped to that tenant; selecting a tenant they don't belong to → 403
ST-21 Logout revokes the session
  • When POST /auth/logout
  • Then the session row is deleted; any reuse of that token yields 401
ST-22 Published post reads are fast at scale
  • Given sustained load on the public read path
  • Then p95 < 150 ms at ≥ 5k reads/s, with most responses served from CDN / server cache without a DB hit (details in section 10)

System architecture

One backend — a modular monolith, framework- and language-agnostic — hosts authentication and content in the same deployable: auth, posts, media, and tenancy are modules in one process, sharing one database and one deploy surface. The posts module also owns document import (PDF · DOCX · Google Docs · open formats → markdown) as a worker job. The API edge authenticates, resolves the tenant, and dispatches to those modules. Everything stateful lives in PostgreSQL with RLS; image bytes live only in R2. Google and GitHub are the only external pieces, and only for the SSO handshake.

Why one DB

A single shared database keeps cross-tenant admin/superuser queries, analytics, and migrations simple. Isolation is enforced inside the database via RLS, so a bug in app code cannot leak rows across tenants. Auth and posts share transaction boundaries — e.g. "sign up → provision membership" commits atomically.

Why R2, not DB blobs

Decision adopted: R2 keeps the DB small (image metadata only), gives no-egress-fee delivery with Cloudflare's CDN, and uploads stream through presigned URLs without touching the API's memory. Key scheme below.

Auth ships in the backend

Authentication is a module of the same backend as posts — one process, one DB, one deployment. No third-party identity service: sessions are validated against Postgres on every request. Only the SSO handshake talks to Google/GitHub.

Multi-tenancy model

Tenants are resolved from the subdomain or request header for public reads, and from the authenticated session's active tenant for admin writes. Data separation is database-enforced.

Shared schema + RLS

Adopted

Every row carries tenant_id. Postgres policies auto-append WHERE tenant_id = current_tenant().

  • One migration path, trivial cross-tenant admin
  • Superuser role bypasses policies — exactly the "see all tenants" case
  • Set session tenant via SET LOCAL app.tenant_id
  • Best fit: hundreds to low-thousands of tenant sites

Schema-per-tenant

Each tenant gets a schema (alpha.posts, …).

  • Hard isolation, per-tenant backup/restore
  • Migrations × N; cross-tenant queries painful
  • Superuser view needs cross-schema queries/views
  • Only pays off with strict regulatory isolation

Database-per-tenant

Separate logical database per tenant.

  • Strongest blast-radius isolation
  • Highest ops cost: provisioning, pooling, migrations
  • Superuser = routing layer across N pools
  • Reserved for enterprise/isolated customers

Superuser visibility

The platform role super_admin grants a session a "global tenant" scope, bypassing RLS policies (implemented via a security definer or policy owner). All other sessions are permanently RLS-scoped to one tenant, even privileged tenant admins.

Authorization model

Two layers: RLS decides which rows you may see, RBAC decides which actions you may take. Both scopes derive from the same membership table. The post is the authorization object — every post is created in a tenant with an author, and per-role capability is evaluated against the post's tenant + status.

Capability Guest Author Editor Admin Owner Super admin
Read published posts (any reader UI)✔✔✔✔✔✔ (all tenants)
Create drafts–✔✔✔✔✔ (any tenant)
Edit own drafts–✔✔✔✔✔
Edit any post in tenant––✔✔✔✔
View drafts–own✔✔✔✔
Publish / unpublish––✔✔✔✔
Manage members & roles–––✔✔✔ (global)
Manage tenant settings–––✔✔✔
Delete tenant / posts––––✔✔

Row access is enforced by RLS; cell-level actions by a middleware role check in the service layer. Never the reverse.

Post lifecycle & rules

  • draft → only author/editor/admin/super_admin can read
  • published → guest-readable via public API
  • archived → hidden from public listing, still editable by editor+
  • Longevity rules (scheduling, unpublish-on-date) live as job handlers, not in the schema

Membership keys these tables

Actor = memberships(tenant_id, user_id, role). Authorization is a single query: check membership role against the post's tenant, compare against the permission matrix. Super_admin short-circuits before RLS applies.

Authentication & SSO

Authentication is a module of the same backend that serves posts — one process, one database, one deployment. It is not a separate identity service: sessions are validated against Postgres on every request, and a single transaction can create a user, provision a membership, and issue a session atomically. Google and GitHub are the only external parties in the auth path, and only for the SSO handshake.

Password sign-in (optional)

  • POST /auth/signup, POST /auth/login
  • Argon2id hashing (or bcrypt); never store plaintext
  • Rate-limited, lockout after N failures on the login endpoint
  • Issues the same session token as SSO — one token model, no special-casing

Google & GitHub SSO

  • Authorization Code + PKCE on both; state binds the callback to the start
  • Google via OIDC subject; GitHub via app user id — persisted in identities
  • First sign-in → create user, link identity, consume invitation/auto-member via verified email
  • Subsequent sign-ins → idempotent upsert, map to existing memberships
  • Emails are normalized (lowercase, trimmed) before any matching

Token strategy — opaque DB sessions

Opaque sessions in DB (adopted)

  • Random token hashed into sessions; instant revoke (logout / role change / breach)
  • Resolves actor's active tenant at request time — membership edits take effect immediately
  • Sent as HttpOnly + Secure cookie (SameSite=Lax) with CSRF protection, or Authorization header for native/admin clients

Stateless JWT (rejected here)

  • No per-token revocation; carries tenant/role claims that go stale
  • Role or tenant membership changes require re-issuance, and orphaned tokens stay valid until expiry
  • Fine when auth is external and tenant scope is static — not our case

Upload security

  • Presigned URLs: short TTL (15 min), scoped to exact key
  • MIME + max-size validation server-side at confirm
  • Confirm creates the row and enqueues resize/WebP variant jobs (retried by the worker)
  • Orphan objects cleaned by a sweeper job

Delivery

  • Served read-only from CDN; no API round trip per image
  • Variants generated at upload/confirm time by a worker (resize 480/800/1200 + WebP); sizes live in post_images.variants
  • Reader UIs build responsive srcset from the variant list; caching via long-lived content-hashed URLs

Document import — PDF · DOCX · Google Docs · open formats

Authors bring in an existing document and land in the editor as a markdown draft, not raw pasted text. Conversion is async (same worker path as image variants) and never writes a partial post; a finished conversion is previewed, then applied as a draft under the normal ST-5 rules (ST-23). Google Docs reuses the author's linked Google identity to export the document — no new sign-in, but the drive.readonly export scope must be consented at login.

SourceApproachFidelity
DOCXdocx → HTML → markdown (pandoc family); styles map to GFM semantics (headings, code, links, lists).High — round-trips to a clean draft

The conversion backend is a job the posts module owns (same worker pool as variants). Output goes through the exact sanitization and rendering pipeline as hand-written markdown, so an imported document can never smuggle raw HTML into a reader page.

Performance & horizontal scalability

The API is horizontally scalable because compute is stateless: every request-scoped artifact (session token, PKCE verifier, OAuth nonce, active tenant scope) is written to shared Postgres, so any replica can serve any request — no sticky sessions, no in-process locks, no shared local state. Adding capacity is just adding replicas behind the load balancer. Auth is a module of this same stateless backend (section 3), so identity traffic scales on the same replicas as post traffic.

DB ceiling managed

  • PgBouncer pools the connection fan-in from N replicas
  • Read replicas absorb the public read path; writes (rare) go to the primary, where RLS lives
  • Image bytes live in R2, never in the DB — small working set, cacheable indexes

Background work stays off-path

  • Cache purge, media sweeper, replica warm-up, and document import run as retried worker jobs
  • API never blocks on them; a failed purge retries and self-heals
  • Rate limiting per tenant + global on auth & mutation endpoints for load safety

Consistency at the edges

Publish writes to the primary, then enqueues purge + replica sync. Because a public read can arrive microseconds later, single-post public reads hit the primary or a warm cache until the purge completes; list reads tolerate ≤ ~1s replica lag. Net effect (ST-9/ST-10): a reader never sees a just-published post vanish, nor an unpublished post linger, for more than one purge cycle.

UI strategy

Admin & editor client

One SPA (any stack) used by authors, editors, admins, and superadmins; role-aware rendering of the permission matrix.

  • Session switcher for superadmins (global tenant scope)
  • Interactive markdown editor: rendered preview updates on each keystroke, and clicking a rendered block drops you back into its markdown source for editing — details below
  • Image dropzone → presign/confirm, document import upload, OAuth buttons (Google/GitHub) + password form on the same screen

Reader sites (multiple)

Independent UIs, each bound to one tenant slug in deploy-time config. SSR renders markdown HTML from the public API.

  • Revalidate/ISR so CDN connects published posts as fast as possible
  • Rendering: server-side GFM → sanitized HTML with syntax highlighting (never client-render raw markdown)
  • Images use responsive srcset from post_images.variants
  • A reader site never touches the admin API or any credential

Interactive markdown editor — draft authoring (adopted)

The editor client is a bidirectional markdown editor: editors write in markdown, see the rendered post update on every keystroke, and can click any rendered piece to drop back into its markdown source and edit it in place. It is the authoring surface for ST-5 / ST-6 / ST-9 / ST-11 and the import review step (ST-23).

  • Live preview parity. Each change re-renders the preview (≈150 ms debounce) with the same GFM renderer spec as readers — same sanitization and highlighting theme. It renders the active draft only; the HTML guests read is still produced at publish time (render-on-publish). Golden tests lock the preview output to published output so the two can never drift.
  • Click-through editing. The renderer emits per-block source metadata (each rendered block ↔ its markdown start/end offsets). Clicking a rendered heading, paragraph, quote, code block, or image toggles that block back into an inline markdown editor scoped to exactly its source range; editing re-renders just that block and the cursor stays put.
  • Inline image flow. An image in the preview — or a toolbar button — opens the dropzone → POST /admin/media/presign → PUT to R2 → confirm → the ![alt](cdnUrl) markdown is inserted at the cursor.
  • Metadata + autosave. Slug, excerpt, tags, and cover image live in a side panel; edits autosave (debounced PATCH /admin/posts/:id) with a saved indicator. Only the author's own drafts open per ST-6.

RLS hardening checklist — how it can't silently leak
  1. Force it on, every table. ALTER TABLE … ENABLE ROW LEVEL SECURITY; and FORCE ROW LEVEL SECURITY; so even the table owner is subject to policies — ownership churn is the classic way RLS gets silently bypassed.
  2. Fail-closed tenant scoping. One function current_tenant() reads current_setting('app.tenant_id', true), set via SET LOCAL inside each request's transaction. Session-level SET is banned — a pooled/reused connection must never carry a stale tenant.
  3. No catch-all policy. Every tenant-scoped table gets exactly one default-USING policy matching current_tenant() = tenant_id. If the setting is absent the policy matches nothing → a leaked/guest call breaks loudly instead of silently returning rows.
  4. Writes are checked too. Policies use WITH CHECK, not just USING, so INSERT/UPDATE cannot create or move rows into another tenant.
  5. Super_admin is explicit, not accidental. The platform role gets BYPASSRLS (or policy-owner) — a named, reviewed precedent, never an ad-hoc SUPERUSER workaround. Everything else stays inside policies.
  6. Contract tests assert non-leak. One "cannot see other tenant" test per role (guest/author/editor/admin) keyed to ST-2, ST-3, ST-6, ST-20: a cross-tenant GET/PATCH/INSERT must return 0 rows / 403.
  7. Migration lint. A CI check iterates every tenant-scoped table and fails the build if it lacks ENABLE+FORCE and a policy referencing current_tenant().
