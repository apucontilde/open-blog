Implementation plan · pre-code · v0

A seeded, same-origin editor UI and a one-command dev stack

The API already serves authentication, tenancy, and posts. This plan adds the smallest UI that can exercise it — sign in, create a tenant, create/edit/view a post — plus a docker-compose that boots Postgres, the API, a one-shot seed, and an nginx-served UI. The browser only ever talks to one origin, so the existing HttpOnly session cookie just works.

The seeded super admin currently cannot author a post

Verified in internal/authz/actor.go:38: any super_admin resolves Platform = true with Tenant = nil, and posts.Create then fails ErrNoTenant (internal/posts/service.go:71). So POST /admin/tenants (platform-only) and "create a post" (tenant role) cannot be done by the same seeded user today. Section 4 fixes this.

Assumptions adopted for this review

  • UI = one vanilla HTML/CSS/JS page; Tailwind + DaisyUI via CDN, no bundler
  • Auth = existing HttpOnly session cookie (same origin), no token storage in JS
  • One origin in dev: nginx in the ui container reverse-proxies /auth /admin /public
  • Seed is an idempotent one-shot process (cmd/seed), not auto-signup
  • Seeded super admin can assume owner in any active tenant (ST-18)
  • Out of scope: images/R2, document import, Google/GitHub SSO, member admin, signup, password change

3

System shape

One public origin (http://localhost:8080) is the ui container. nginx serves the static page and forwards API paths to api:8080 on the compose network. Because the browser and API share an origin, the session cookie (HttpOnly, SameSite=Lax) is sent automatically and no CORS or token storage is needed. 

flowchart LR
    B["Browser\nhttp://localhost:8080"] -->|"GET /index.html · app.js"| UI["ui · nginx:alpine\nstatic + reverse proxy"]
    UI -->|"/auth/* · /admin/* · /public/*"| API["api · Go net/http\n:8080 (internal)"]
    API -->|"pgx · RLS per request"| DB[("db · postgres:16\nvolume pgdata")]
    API -->|"goose.Up on startup"| DB
    SEED["seed · one-shot cmd/seed\nuser + tenant + owner"] -->|"idempotent upserts"| DB
    API -.->|"readiness gate"| UI

Why same-origin nginx

The API already issues an HttpOnly cookie. Reverse-proxying avoids CORS credentials, cookie-domain juggling, and CSRF-on-cross-site concerns entirely, while keeping ui a separate, replaceable service.

Why a seed process

Bootstrapping a platform admin needs DB writes that no public endpoint should expose. A dedicated cmd/seed reuses the same argon2 parameters and is safe to re-run on every compose up.

Why the authz fix is required

Without it, the one seeded user can either create tenants or create posts, never both. The fix is small and moves the code toward the already-written ST-18 ("super admin switches active scope and acts").

4

Required API changes

Four focused backend edits (plus two new files). None changes an existing request body or success response shape; the only behavioral change is that a super admin with an explicit active tenant now acts as that tenant's owner instead of resolving to an unusable platform-only actor.

4.1 internal/authz/actor.go — tenant scope wins over platform fallback

Today the super-admin branch returns before the membership branch, discarding the active tenant. The new order: resolve the super bit, then branch on whether an active tenant exists.

4.2 internal/authz/scope.go — bypass RLS only when unscoped

A scoped super admin must stay inside tenant RLS; only a platform-only actor (no active tenant) gets cross-tenant reads. Tenant management handlers keep checking actor.Platform, not the scope.

4.3 internal/api/handlers.go — /auth/me memberships & platform tenant switch

The UI cannot guess tenant ids. /auth/me gains a memberships array (tenant id, slug, name, role); and PUT /auth/me/active-tenant skips the membership check for platform actors.

4.4 internal/store/store.go — membership read model

Mirrors the existing Memberships helper but joins tenants for the slug the public-view link needs.

4.5 internal/auth/password.go — export the hasher

The seed process must produce an argon2id hash identical in shape to runtime signup.

Decisions — confirmed

All four defaults were confirmed in review and are now baseline; annotate any card to reopen one.

✓
Confirmed: D1 vanilla + Tailwind CDN · D2 HttpOnly cookie · D3 nginx single origin · D4 super admin assumes owner in the active tenant.
D1

How the UI is built & styled

Confirmed Vanilla HTML/CSS/JS + Tailwind/DaisyUI CDN — zero build; ships as 3 static files. Add a bundler later if it grows.
D2

Session transport in the browser

Confirmed HttpOnly cookie via same-origin fetch — uses the login Set-Cookie; the token is never exposed to JS.
D3

How browser reaches the API

Confirmed nginx single-origin reverse proxy — ui at :8080 proxies /auth /admin /public to api:8080; no CORS and no CSRF surface.
D4

How the platform super admin gets authoring rights

Confirmed Super admin assumes owner in the active tenant (ST-18) — one seeded user creates a tenant and immediately writes in it; no extra membership rows.
11

Risks & notes

RiskAssessmentMitigation
Actor change alters auth behavior A scoped super admin now carries a tenant role; unscoped behavior is unchanged. Add cases to resolve_actor_test.go and the httptest contract suite for ST-17/ST-18 before wiring the UI.
No CSRF token Mutations ride the session cookie; the API has no anti-CSRF token today. Single origin + SameSite=Lax blocks cross-site POSTs for this dev UI. If D3 becomes separate-origin, add a CSRF token before exposing beyond localhost.
Tailwind browser CDN in the UI Runtime JIT adds weight and needs network on first load. Acceptable for a dev UI; swap to a compiled stylesheet (or drop to plain CSS) when this becomes a real admin app.
Seed password in env Compose defaults are weak and there is no change-password endpoint. Treat as dev-only; require a real SEED_PASSWORD outside localhost and add password change in a later module.
Preview is save-then-render The editor shows content_html only after a successful create/save, not per keystroke. Intentional for "very simple"; the original plan's keystroke editor (section 11 of the API plan) is the upgrade path and needs a render endpoint or client renderer with golden parity.
Admin list unpaginated GET /admin/posts returns every visible post. Fine for dev volumes; add cursor/limit support when post counts grow.

Acceptance & verification

Manual flow (the definition of done)

  1. cp .env.example .env, set SESSION_KEY
  2. docker compose up --build
  3. Open http://localhost:8080, sign in as the seeded user
  4. Seeded tenant auto-selected; create a post, edit it, publish it
  5. "View public" renders the post from /public/...
  6. Create a new tenant, auto-switch, create a post in it
  7. Sign out returns to the login screen; reload keeps the session until logout
